## О проекте
iOS-клавиатура, которая шифрует сообщения перед отправкой в любом мессенджере: текст набирается внутри клавиатуры, в чат уходит только шифротекст, получатель расшифровывает его той же клавиатурой. Пары ключей как в PGP, свой формат на CryptoKit, без сервера и без сети. Подробно — в IDEA.md.

## Стек
Swift 6 · iOS 18+, только iPhone · SwiftUI (приложение) + UIKit `UIInputViewController` (расширение клавиатуры) · Apple CryptoKit · Keychain и App Group для данных, общих с клавиатурой · тесты: Swift Testing (ядро), XCTest/XCUITest (UI) · линтер и форматтер: swift-format из Xcode · Xcode 27.2. Сторонних зависимостей нет.

## Платформа и интерфейс
Платформа: ios
- Где открыть приложение: `scripts/run.sh` → iOS Simulator «iPhone 17»
- Чем проверять интерфейс: инструмент iOS Simulator (скриншоты, нажатия, ввод текста) и XCUITest (`scripts/test.sh ui`)
- Рамки макетов: iPhone 375–440 pt, светлая и тёмная тема; клавиатура — внутри экрана мессенджера
- Песочница — это: новый чистый симулятор без ключей и контактов (`scripts/sandbox.sh start` / `stop`)

## Соглашения
- `App/` — приложение (SwiftUI); `Keyboard/` — расширение клавиатуры; `UITests/` — XCUITest; `Packages/CipherCore/` — крипто-ядро и форматы (Swift-пакет, тесты в `Tests/`, гоняются на Mac без симулятора).
- Папки `App/`, `Keyboard/`, `UITests/` подключены к таргетам как synchronized groups: новый .swift-файл в папке сам попадает в таргет. `project.pbxproj` правим только ради настроек сборки, таргетов и зависимостей.
- Вся криптография и разбор форматов — только в CipherCore; приложение и клавиатура CryptoKit напрямую не импортируют.
- Открытые ключи из ввода принимаются только через проверку `PublicKey` в CipherCore (малый порядок + каноничность); `Fingerprint.short` — только для показа, сверка ключа — по полному отпечатку.
- Сети нет вообще: сетевые API запрещены, `scripts/lint.sh` на них падает.
- Открытый текст сообщения — только в памяти: никаких `print`/`Logger`, `UserDefaults`, файлов, буфера обмена.
- Секреты: приватные ключи — только в Keychain. Team ID для подписи на устройство — локально в Xcode, не в git.
- UI-проверки идут в iOS Simulator, а не в браузере: eval типа `ui` — сценарий в симуляторе (XCUITest или нажатия и скриншоты через инструмент симулятора), `design` — скриншот симулятора против макета.
- `accessibilityIdentifier` у ключевых элементов — по ним пишутся UI-тесты (`app.title`, `keyboard.encrypt`, …).
- Тексты интерфейса — на русском.
- Идентификаторы: приложение `dev.cipherkeyboard.app`, клавиатура `dev.cipherkeyboard.app.keyboard`, App Group `group.dev.cipherkeyboard`.

## Не делаем (non-goals)
- Сеть, сервер, аккаунты, синхронизация, аналитика, реклама.
- Совместимость с OpenPGP/GPG, шифрование по паролю.
- Хранение расшифрованных сообщений и истории переписки.
- iPad, Android, macOS; автокоррекция и подсказки слов в клавиатуре.

## Как мы работаем
Не менять без причины — на этом держатся скиллы и хуки в `.claude/`.

**Конвейер фичи** (статусы в `specs/<фича>/requirements.md`):
`/write-evals` → пользователь смотрит evals и макет → `/approve` → `/review-loop` → (medium/high: `/approve`) → готово.
Статусы: `draft → in-review → approved → building → verified → done`. Где мы сейчас — `/pipeline`.

1. **Сначала контракт, потом код.** Код фичи пишется только после того, как пользователь одобрил её evals (`approved`). Одобряет только пользователь — командой `/approve`.
2. **Доказательство, а не «готово».** Никогда не говори, что сделано, без вывода тестов/команд или того, что видно в интерфейсе (браузер, симулятор — см. «Платформа и интерфейс»). Фича готова, только когда все её evals в статусе `pass` — это проверяют хуки.
3. **Строит один, проверяет другой.** Строитель (`builder`), проверяющий (`verifier`) и ревьюер (`reviewer`) — разные агенты в свежих контекстах. Статус `pass` у eval ставит только verifier.
4. **Строгость по риску.** Перед evals каждая фича получает риск (`/classify-risk`): low / medium / high. Чем выше риск, тем больше evals, глубже ревью и обязательнее приёмка человеком.
5. **Повторяющаяся ошибка → правило.** Если ревью находит одно и то же или баг проскочил — предлагай одну строку в REVIEW.md → «Выученные правила». Добавляй только с одобрения пользователя.
6. **Баг** → `/fix-a-bug`: воспроизвести → доказать причину → исправить → регрессионный eval.
7. **Свежий взгляд** → `/first-time-user <фича>`: агент без доступа к коду проходит приложение как новый клиент (для high обязательно).
8. **Мелкая правка** (опечатка, текст, цвет) — можно без цикла: правка → тесты и линтер → коммит `[ok]`. Всё, что меняет поведение, — через фичу или `/fix-a-bug`.

**Git** (обязателен — на нём держится откат):
- `main` всегда рабочий. Фича — ветка `feature/<id фичи>`, багфикс — `fix/<кратко>`.
- Каждая рабочая версия (тесты и линтер зелёные) — коммит с префиксом `[ok]`; незавершённое — `[wip]`. По `[ok]`-коммитам `/fix-a-bug` ищет, где сломалось.
- В `main` фича попадает одним merge-коммитом `git merge --no-ff`, поэтому откат всей фичи — одна команда: `git revert -m 1 <sha>`.
- Нельзя без явной просьбы пользователя: `push --force`, `reset --hard`, переписывание истории `main`, удаление веток.
