## 1. Что проверено и в порядке

### 1.1 Крипто-ядро (`Packages/CipherCore/Sources/CipherCore`)

- **Схема.** X25519 (эфемерная пара на сообщение) → HKDF-SHA256 с info = домен ‖ E_pub ‖ R_x → ChaCha20-Poly1305
  заворачивает случайный ключ сообщения K; текст шифруется производной K с AAD = заголовок ‖ ключ отправителя ‖ E_pub ‖
  все записи ‖ обязательство; подпись Ed25519 над доменной строкой ‖ всеми байтами. Это корректный «encrypt-then-sign» с
  привязкой отправителя внутрь AAD (`CipherMessage.swift:82-87`), поэтому классическая атака «снять подпись и
  переподписать своим ключом» ломает расшифровку текста — и это покрыто тестом «Ключ отправителя заменён на ключ M…»
  (`TamperTests.swift:115`).
- **Обязательство на ключ** (`CipherMessage.swift:123,228`) закрывает атаку с многоключевым тегом Poly1305 (разные
  тексты разным получателям под одной подписью); сравнение в постоянном времени (`:233-240`); тесты
  `TamperTests.swift:296,314,388,401`.
- **Порядок проверок** (`CipherMessage.swift:97-161`): формат → проверка ключа отправителя и эфемерного ключа →
  подпись → своя запись (перебор всех без досрочного выхода, >1 раскрывшейся = tampered) → обязательство → текст →
  дата → дополнение → UTF-8. Частично расшифрованный текст наружу не выходит.
- **Ключи из недоверенного ввода.** `PublicKey.swift:21-26,88-136`: каноничность X25519 (старший бит, `< p`), точки
  малого порядса через пробный скаляр (CryptoKit отвергает нулевой секрет), для Ed25519 — `y < p` и список
  `ge25519_has_small_order` из libsodium (7 кодировок, совпадает с libsodium). Эфемерный ключ проверяется тем же
  `isUsableAgreementKey` (`CipherMessage.swift:108`). Тесты: `PublicKeyTests.swift:157-229`,
  `MessageParsingTests.swift:134`, `TamperTests.swift:222,232`.
- **Разбор** (`Envelope.swift:143-189`, `TextEncoding.swift`): строгий канонический base64url, длина определяется из
  заголовка, читается ровно столько символов, сколько нужно, верхняя граница 20 000 символов, 1 000 000 «A» —
  быстрее секунды (тест `MessageParsingTests.swift:105,115`). Подмена любого байта и любого символа — тесты
  `TamperTests.swift:44,69`.
- **Дополнение до 32 байт**, настоящая длина внутри шифротекста, ненулевое дополнение → tampered
  (`SealOpenTests.swift:185-203`).
- **`Identity`** не `Codable`, `CustomReflectable` пустой, приватные байты только через `package`-метод
  (`Identity.swift`); тесты `IdentityTests.swift:62-89` проверяют, что приватные половины не видны ни в hex, ни в
  base64.
- **Nonce.** Для записи получателя — нулевой при одноразовом KEK (новый эфемерный ключ на сообщение, R_x в info);
  для текста — случайный 96-бит при случайном одноразовом K. Повторов быть не может.

### 1.2 Хранилища

**[Важно] [лимит-сообщения] `Packages/CipherCore/Sources/CipherCore/CipherMessage.swift:25` — тексты длиннее 2720 байт не помещаются в одно сообщение Telegram.**
Доказательство: размер `ckmsg2` для получателя и себя — `T = 330 + Lp` байт (FORMAT.md), в тексте
`7 + ⌈4T/3⌉` символов. При `Lp = 4096` это 5909 символов, при пороге Telegram 4096 символов клиент разрежет
сообщение на два, получатель скопирует одно — получит «Сообщение повреждено или подделано» (обрезка → `malformed`,
`Envelope.swift:185`). Если скопировать оба сообщения разом, Telegram вставит между ними имя и дату, а буквы имени
входят в алфавит base64url — разбор всё равно упадёт. Предел, при котором всё влезает: `T ≤ 3066` → `Lp ≤ 2720` →
**2720 байт UTF-8 (≈1360 букв кириллицы)**. IDEA.md называет Telegram первым сценарием, а счётчик байт появляется
только после 3500 (`KeyboardInput.swift:18`), то есть пользователь узнаёт о проблеме от собеседника.
Исправление (минимальное, без смены формата и evals 05/06): добавить в `CipherMessage` константу
`public static let singleMessageBytes = 2720` с комментарием-расчётом; в `KeyboardInput.counter` показывать счётчик
с 2000 байт, а при `byteCount > CipherMessage.singleMessageBytes` — текст вида «3100 / 4096 байт · длиннее одного
сообщения Telegram»; в `EncryptInsertCoordinator.status` ту же подсказку вместо «Готово к шифрованию».
Исправление (правильное, через фичу): снизить лимит набора до 2720 байт в `KeyboardInput.insert`
(`KeyboardInput.swift:44`) и в `EncryptInsertCoordinator.begin` (`EncryptInsert.swift:167`), оставив `open` принимать
до 4096 (формат не меняется, старые сообщения читаются). Это меняет контракт 05/06 → `/write-evals` на мини-фичу
«лимит одного сообщения», затем цикл. Какой вариант — ваше решение; минимальный можно сделать как мелкую правку.
Тот же класс также: `App/DecryptView.swift` — нет.

### Мелочь

**[Мелочь] [нет-валидации] `Packages/CipherCore/Sources/KeyboardTyping/Decrypt.swift:92,225` — для неизвестного отправителя показываются только 32 бита отпечатка.**
Доказательство: `fingerprintText` по умолчанию — `$0.fingerprint.short` (2 группы = 9 символов = 32 бита);
результат «От неизвестного ключа 3CE9 D861». Подобрать ключ с нужными 32 битами — около 2³² хешей SHA-256,
минуты на ноутбуке. Злоумышленник, зная короткий отпечаток контакта «Борис» (он виден в списке контактов и
в выборе получателя), может прислать сообщение, где «неизвестный ключ» выглядит как ключ Бориса, и расчёт на то,
что пользователь подумает «это Борис, просто контакт слетел». CLAUDE.md прямо говорит: «`Fingerprint.short` —
только для показа, сверка ключа — по полному отпечатку»; именно сверку пользователь здесь и делает глазами.
Исправление: в `Decrypt.swift:92` заменить значение по умолчанию на `{ $0.fingerprint.description }` (39 символов,
128 бит; `sender.numberOfLines = 0` уже стоит, `DecryptUIKit.swift:77`). В приложении и клавиатуре текст станет
«От неизвестного ключа 3CE9 D861 1272 B2A6 0720 1589 E865 3A98». В `DecryptTests.displayFingerprintCollisionDoesNotAssignContact`
добавить проверку, что строка по умолчанию содержит полный `fingerprint.description`. Обновить макет 07 и строку в
`requirements.md` 07, если там зафиксирован короткий вид.
Тот же класс также: `EncryptionControls.swift:17,28` и `ContactsView.swift:72,92` показывают `short` в списках
своих контактов — там это допустимо (выбор среди своих же записей), но можно поднять до 4 групп (64 бита) без
изменения вёрстки.

**[Мелочь] [слабый-тест] `scripts/lint.sh:7` — запрет сети держится на узком регулярном выражении и ручном запуске.**

## 3. Рекомендации и ограничения (вне формата ревью — не блокируют, решать вам)

3.1 **Запомненный получатель между сессиями** (`EncryptInsert.swift:122-128`, требование AC2 фичи 06). Клавиатура
открывается в чате с Борисом, а «Кому:» уже стоит вчерашняя Вера. Если нажать «Зашифровать» не глядя, текст уйдёт
в чат Бориса, зашифрованный для Веры: Борис его не прочитает, а Вера прочитает, если ей перешлют. Утечки «в
мессенджер» нет, интерфейс крупно показывает получателя и успех «Зашифровано для …», так что это осознанный
компромисс. Более строгий вариант — помнить выбор только внутри одной сессии клавиатуры (сбрасывать в `hide()`,
`EncryptInsert.swift:152`) или хотя бы при смене хозяина. Это изменение AC2 → через `/write-evals`.

3.2 **Поддержка `ckmsg1`** (`Envelope.swift:6`, `CipherMessage.swift:97-99`, `GoldenVectorTests`). Формат v1 никогда не
выпускался, но принимается — это лишняя поверхность разбора и сообщения «без даты». Перед первым выпуском проще
оставить только `timestamped = 2`: удалить `case legacy`, вектор v1 и тесты на него, в FORMAT.md оставить историю одной
строкой. Тогда `ckmsg1:` → `unsupportedVersion`.

3.3 **Нет способа создать новый ключ** (`IdentityStorage.swift:8-15` — намеренно нет update/delete). Если приватный ключ
скомпрометирован или пользователь хочет «начать заново», единственный путь — стереть iPhone: запись в Keychain
переживает удаление приложения. Это записанный non-goal, но для «законченного» продукта стоит запланировать фичу
«Новый ключ» (с двойным подтверждением, предупреждением «старые сообщения не прочитать» и напоминанием заново
разослать открытый ключ). Отзыв без сервера невозможен — только «сообщите собеседникам».

3.4 **Буфер обмена читается целиком до проверки лимита** (`DecryptUIKit.swift:18`, лимит 65 536 байт проверяется
после, `Decrypt.swift:190`). API размера у `UIPasteboard` нет, поэтому дешёвого исправления нет; при многомегабайтном
буфере расширение может упереться в лимит памяти, и iOS подменит клавиатуру системной — без утечки, но неприятно.
Проверить на устройстве (см. чек-лист выше, п. 6); если воспроизводится, единственный вариант — читать через
`itemProviders.first?.loadDataRepresentation(forTypeIdentifier: UTType.utf8PlainText.identifier)` и обрывать по
размеру `Data`, что тоже грузит данные, но без удвоения под `String`.

3.5 **Асимметрия резервных копий.** Ключ (`ThisDeviceOnly`) входит в зашифрованную локальную копию и восстанавливается на
то же устройство; контакты исключены из копии (`ContactStore.swift:107-112`). После восстановления на тот же iPhone
пользователь получит свой ключ и пустые контакты и решит, что «всё сломалось». IDEA.md считает, что ключ «не покидает
устройство», — это верно только для другого устройства. Исправлять код не нужно; стоит написать это на экране
«Настройка» одной строкой («При переносе на новый iPhone ключ и контакты не переносятся; после восстановления из
копии контакты нужно добавить заново») и в политике конфиденциальности.

3.6 **Нет прямой секретности, нет отрицаемости, нет ротации** — честно описано в IDEA.md («Границы защиты»).
Для мессенджерного сценария это ожидаемо для PGP-подобной схемы; если захочется, следующий шаг — периодическая смена
пары ключей (та же фича «Новый ключ»), а не ratchet.

3.7 **Биометрия перед расшифровкой** — открытый вопрос IDEA.md. В расширении клавиатуры `LAContext` показывать
системный диалог не может, поэтому привязывать запись Keychain к `.biometryCurrentSet` нельзя без потери
расшифровки в клавиатуре; возможна только биометрия в приложении (экран «Мой ключ», вкладка «Расшифровать»). Низкая
ценность при `WhenUnlocked` — отложить.

3.8 **Debug-сборка клавиатуры содержит сетку фикстур** (`KeyboardPanel.swift:272-312`, кнопка поверх строки статуса).
В Release её нет (`#if DEBUG`, проверено аудитом по бинарникам). Правило: на устройства посторонних людей и в
TestFlight — только Release (TestFlight и так принимает только Release).

3.9 **Память.** Открытый текст и ключи живут в `String`/`[UInt8]`/`SymmetricKey`; Swift не даёт гарантий обнуления.
Это общее ограничение платформы, для данной модели угроз (без джейлбрейка) приемлемо; упоминаю, чтобы не обещать
«стирание из памяти» в политике конфиденциальности.

3.10 **`UITextInputMode.activeInputModes` вместо недокументированного `AppleKeyboards`** (`SetupModel.swift:57-58`,
`KeyboardSetup.swift:12-19`). Текущий код сам признаёт, что формат ненадёжен и даёт `unknown`. Apple в манифесте
приватности отдельно предусматривает категорию «Active keyboards» (причина `3EC4.1`) именно для приложений-клавиатур,
проверяющих, включена ли их клавиатура, — это намёк на поддерживаемый путь. Проверить на устройстве, различает ли
`activeInputModes` стороннюю клавиатуру по `primaryLanguage = "mul"`; если да — заменить и добавить категорию в манифест.
