# Крипто-ядро — ключи, шифрование, подпись

## Суть
Библиотека `CipherCore` (`Packages/CipherCore`): создать личность (пару ключей), выгрузить открытый ключ в текст и разобрать обратно, зашифровать текст для получателей с подписью отправителя, найти шифротекст в любом тексте, расшифровать и проверить подпись. Приложение и клавиатура работают с криптографией только через неё.

## Пользовательские истории
- Как отправитель, я хочу, чтобы сообщение мог прочитать только выбранный собеседник и я сам, чтобы мессенджер и посторонние видели лишь шифротекст.
- Как получатель, я хочу знать, от кого сообщение и что его не изменили по дороге.
- Как получатель, я хочу расшифровать сообщение, даже если скопировал его вместе с текстом вокруг или мессенджер разбил его переносами строк.
- Как разработчик приложения и клавиатуры, я хочу простой API без криптопримитивов, чтобы нельзя было ошибиться в их использовании.

## Публичный API
Имена ниже — контракт: на них пишутся тесты и фичи 02, 03, 06, 07. Типы CryptoKit в публичном API не появляются.

```swift
public struct Identity: Sendable {                       // не Codable, не Encodable
    public static func generate() -> Identity
    public init(privateKeyData: Data) throws             // CipherError.invalidKey
    public func privateKeyData() -> Data                 // 64 байта — только для Keychain (02)
    public var publicKey: PublicKey { get }
}

public struct PublicKey: Hashable, Sendable, Codable {   // Codable — как строка ckpub1:…
    public init(string: String) throws                   // invalidKey | unsupportedVersion
    public var string: String { get }                    // "ckpub1:…"
    public var fingerprint: Fingerprint { get }
}

public struct Fingerprint: Hashable, Sendable, CustomStringConvertible {
    public var description: String { get }               // "A1B2 C3D4 … " — 8 групп
    public var short: String { get }                     // первые 2 группы: "A1B2 C3D4"
}

public struct Contact: Hashable, Sendable, Codable, Identifiable {
    public var id: UUID
    public var name: String
    public var publicKey: PublicKey
}

public enum CipherMessage {
    public static let maxPlaintextBytes = 4096
    public static let maxRecipients = 16                 // вместе с отправителем
    public static func seal(_ text: String, from: Identity, to: [PublicKey]) throws -> String
    public static func open(_ text: String, as: Identity, contacts: [Contact]) throws -> OpenedMessage
}

public struct OpenedMessage: Sendable {
    public let text: String
    public let senderKey: PublicKey
    public let sender: Sender
}

public enum Sender: Sendable, Equatable {
    case me                                              // отправитель — личность, которой открыли
    case contact(Contact)                                // ключ отправителя совпал с ключом контакта
    case unknown(Fingerprint)                            // подпись верна, отправителя нет в контактах
}

public enum CipherError: Error, Equatable, Sendable {
    case invalidKey, unsupportedVersion
    case noMessage, malformed, tampered, notARecipient
    case emptyMessage, messageTooLong(byteCount: Int), noRecipients, tooManyRecipients
}
```

## Критерии приёмки

### Личность и открытый ключ
- AC1: `Identity.generate()` создаёт личность из ключа согласования X25519 и ключа подписи Ed25519 (CryptoKit). Две генерации дают разные открытые ключи и разные отпечатки.
- AC2: `privateKeyData()` — ровно 64 байта: сырой приватный X25519 (32) + сырой приватный Ed25519 (32). `Identity(privateKeyData:)` из них восстанавливает личность с тем же открытым ключом. Длина не 64 байта → `invalidKey`.
- AC3: Открытый ключ — одна строка `ckpub1:` + base64url без паддинга от 64 байт: публичный X25519 (32) + публичный Ed25519 (32), всего 7 + 86 = 93 символа. `PublicKey(string:)` разбирает её обратно в равный ключ.
- AC4: Разбор ключа: символы из `CharacterSet.whitespacesAndNewlines` (пробел, перевод строки, неразрывный пробел…) удаляются в любом месте, включая префикс; паддинг `=` на конце принимается. Всё остальное должно быть ровно одним ключом: текст вокруг, другая длина, чужой префикс, строка `ckmsg1:…`, пустая строка, неканонический base64 (ненулевые лишние биты в последнем символе) → `invalidKey`; `ckpub2:` и любая другая версия → `unsupportedVersion`.
- AC5: Ключ, у которого часть X25519 — 32 нулевых байта или другая точка малого порядка (общий секрет с ней всегда известен), → `invalidKey`.
- AC6: Отпечаток — первые 16 байт SHA-256 от тех же 64 байт открытого ключа (X25519 + Ed25519), 8 групп по 4 hex-символа в верхнем регистре через один пробел (39 символов). `short` — первые 2 группы (9 символов).
- AC7: `String(describing:)`, `String(reflecting:)`, `"\(identity)"` и `dump` личности выводят только `Identity(<отпечаток>)` и не содержат приватных байтов ни в hex, ни в base64, ни в base64url. Личность не `Encodable`. Приватная часть отдаётся только `privateKeyData()`.

### Шифрование
- AC8: `seal` возвращает одну строку `ckmsg1:` + base64url без паддинга: регулярное выражение `^ckmsg1:[A-Za-z0-9_-]+$`, без пробелов и переводов строк.
- AC9: Ядро само добавляет отправителя в получатели; повторы в `to` и сам отправитель в `to` шифруются один раз (длина `seal(to: [B, B, A])` равна длине `seal(to: [B])`). `to: [A]` (только себе) — допустимо.
- AC10: Шифротекст не содержит открытого текста: ни как подстроку, ни в base64/base64url при любом из трёх сдвигов. В декодированных байтах нет открытых ключей получателей и их отпечатков — по сообщению не видно, кому оно. Открытый ключ отправителя в сообщении есть (нужен для проверки подписи).
- AC11: Два шифрования одного текста одному получателю дают разные строки.
- AC12: Пустой текст → `emptyMessage`; больше 4096 байт UTF-8 → `messageTooLong(byteCount:)` с фактическим числом байт; ровно 4096 — шифруется; `to: []` → `noRecipients`; больше 16 различных получателей вместе с отправителем → `tooManyRecipients`. Текст из одних пробелов и один символ — шифруются.
- AC13: Шифротекст 100 символов кириллицы для одного получателя (плюс себя) — не длиннее 800 символов.

### Расшифровка
- AC14: Каждый получатель и сам отправитель получают исходный текст байт в байт (сравнение `Array(text.utf8)`, без нормализации Unicode): кириллица, составные эмодзи, `\n` и `\r\n`, буква с отдельным комбинирующим знаком, текст из пробелов, ровно 4096 байт.
- AC15: Личность, которой нет среди получателей, получает `notARecipient` — и только если подпись верна; текста в результате нет.
- AC16: Изменение любого одного байта декодированного сообщения → `tampered` или `malformed` для любого получателя и для отправителя; никогда не успех и никогда не `notARecipient`. Замена любого одного символа после префикса другим символом base64url → не успех. Частично расшифрованный текст не возвращается никогда — ни в результате, ни в ошибке.
- AC17: Отправителя нельзя подменить. Сообщение A, в котором подпись заменена подписью M с сохранённым ключом A, → `tampered`. Сообщение A, в котором ключ отправителя заменён ключом M и подпись пересчитана ключом M, → `tampered` для получателя B (содержимое A не выдаётся за сообщение M).
- AC18: Вердикт отправителя: ключ отправителя равен ключу личности, которой открыли, → `.me`; равен `publicKey` контакта из списка (сравнение обеих частей ключа) → `.contact(тот контакт)`; иначе → `.unknown(отпечаток отправителя)`. Контакт с тем же именем, но другим ключом, → `.unknown`. `senderKey` — всегда ключ отправителя.

### Разбор шифротекста из текста
- AC19: `open` принимает любой текст: удаляет все символы `whitespacesAndNewlines` в любом месте, находит первое вхождение `ckmsg<цифры>:` и разбирает сообщение. Формат самоограничен: длина сообщения известна из его заголовка, поэтому текст сразу после сообщения (`ckmsg1:…ok`, `ckmsg1:… спасибо`, `ckmsg1:…\nok`) не мешает. Паддинг `=` на конце принимается. Из двух сообщений в тексте разбирается первое.
- AC20: Нет `ckmsg<цифры>:` (пустая строка, обычный текст, строка `ckpub1:…`) → `noMessage`. Версия не 1 (`ckmsg2:`, `ckmsg10:`) → `unsupportedVersion`. Сообщение обрезано (на 1 символ, наполовину), не base64url, неканонический base64, мусор → `malformed`. Тело длиннее 20 000 символов после префикса не декодируется целиком → `malformed`, без падения. Больше 16 записей получателей в заголовке → `malformed`.

### Формат и код
- AC21: `Packages/CipherCore/FORMAT.md` описывает байтовую раскладку `ckpub1` и `ckmsg1` (поля, длины, порядок, что входит в подпись и в AAD, обязательство на ключ, дополнение текста, порядок проверок при разборе). В тестах есть «золотой» вектор: фиксированные приватные ключи A и B, фиксированная строка `ckmsg1:…` от A для B — она расшифровывается в фиксированный текст; изменение формата без смены версии ломает этот тест.
- AC22: В `Packages/CipherCore/Sources` нет `print(`, `Logger`, `os_log`, `NSLog`, `UserDefaults`, `FileManager`, `UIPasteboard`, `URLSession`, `import Network`; в публичных объявлениях нет типов CryptoKit. В `App/` и `Keyboard/` нет `import CryptoKit`. Все публичные типы `Sendable`, сборка Swift 6 со строгим параллелизмом без предупреждений о `Sendable`.

### Добавлено по итогам security-review (раунд 2)
- AC23: Обязательство на ключ сообщения. Сообщение содержит под подписью обязательство на ключ сообщения K (например, HMAC-SHA256 от K с доменной строкой); после раскрытия своей записи получатель сверяет его в постоянном времени, иначе → `tampered`. Если у получателя раскрывается больше одной записи — `tampered`. Подписанное A сообщение, в котором записи B и C заворачивают разные ключи (K1 ≠ K2), не открывается хотя бы у одного из них (→ `tampered`): два получателя одного сообщения никогда не видят разные тексты.
- AC24: Длина текста скрыта с точностью до 32 байт. Перед шифрованием текст дополняется нулями до длины, кратной 32 байтам (настоящая длина — внутри зашифрованной части); в открытом заголовке только дополненная длина. Тексты от 1 до 32 байт UTF-8 дают шифротекст одной длины, 33 байта — длиннее; «Да» и «Нет» неотличимы по длине. Ненулевое дополнение или настоящая длина больше дополненной → `tampered`. AC13 (≤ 800 символов) по-прежнему выполняется.
- AC25: Каноническая часть X25519. Ключ, у которого в части X25519 выставлен старший бит последнего байта, → `invalidKey` (иначе у одного собеседника две разные строки `ckpub1`, и проверка дублей контактов в 03 обходится). Такой ключ отправителя или эфемерный ключ внутри сообщения → `malformed`.

## Состояния экрана
Экрана нет (ui: no) — проверяется автотестами `scripts/test.sh core` и командами.

## Граничные случаи
- Ровно 4096 и 4097 байт; текст из одних пробелов (разрешён, это содержимое); один символ; пустая строка.
- Получатель — я сам; один и тот же получатель дважды (шифруется один раз); 16 и 17 получателей.
- Строка с пробелами, неразрывными пробелами и переносами посередине, в том числе внутри префикса; строка без префикса; base64 с паддингом `=` и без; текст до и после сообщения; два сообщения подряд.
- Открытый ключ неверной длины, с чужим префиксом, «нулевой» ключ X25519, ключ внутри другого текста.
- 1 МБ мусора после `ckmsg1:` — `malformed` без падения и без зависания.

## Не входит
- Совместимость с OpenPGP, шифрование по паролю, сжатие, вложения.
- Прямая секретность и обновляемые сессии (как в Signal) — у нас статические ключи.
- Защита от повторной отправки старого сообщения (replay): ядро не хранит состояния.
- Скрытие отправителя: открытый ключ отправителя виден в шифротексте любому, кто его видит.
- Хранение ключей и контактов (02, 03) — ядро работает с переданными ему значениями.
- Подпись для человека вокруг шифротекста («🔒 CipherKeyboard: …») — это решает 06; ядро такой текст переживает (AC19).

## Решения, принятые без пользователя
- Схема: случайный ключ сообщения шифрует текст (ChaCha20-Poly1305); для каждого получателя ключ сообщения заворачивается через эфемерный X25519 + HKDF-SHA256 с доменной строкой `CipherKeyboard v1`. Записи получателей не содержат ключей и отпечатков — получатель перебирает записи (их не больше 16).
- Подпись Ed25519 покрывает заголовок, ключ отправителя, записи получателей и шифротекст; ключ отправителя дополнительно входит в AAD шифрования текста — поэтому переподписать чужое сообщение своим ключом нельзя (AC17). Порядок разбора: формат → подпись (`tampered`) → поиск своей записи (`notARecipient`) → расшифровка (`tampered`). Так любая порча байта даёт `tampered`, а не `notARecipient`.
- **Изменено против черновика:** отправителя в получатели добавляет само ядро, а не вызывающий код (06) — так его нельзя забыть.
- Пробелы удаляются в любом месте, включая префикс, — набор `CharacterSet.whitespacesAndNewlines` (с неразрывным пробелом).
- Лимит 16 получателей вместе с отправителем — с запасом над MVP (собеседник + я), ограничивает работу клавиатуры над чужим заголовком.
- Тело длиннее 20 000 символов отбрасывается сразу: максимальное честное сообщение (4096 байт, 16 получателей) — меньше 8 000 символов, а клавиатура ограничена по памяти.
- Вердикт отправителя называется `.contact(Contact)` вместо `verified(contact)` из черновика, плюс случай `.me` — его требует 07 («От: вы ✓»). `Contact` — тип ядра, его хранит 03.
- Тесты — Swift Testing в `Packages/CipherCore/Tests/CipherCoreTests`, с фиксированными векторами для ключа, отпечатка и сообщения.
- **После security-review (раунд 2, решение пользователя «починить сейчас»):** формат `ckmsg1` меняется на месте, без смены версии: он ещё не попал к пользователям. Золотой вектор (E16) перегенерируется один раз под новый формат. Дополнение — до кратного 32 байтам: компромисс между скрытием длины и бюджетом 800 символов (AC13).
- `Fingerprint.short` (32 бита) — только для показа в списках; сверка ключа с собеседником в 03 и 07 — только по полному отпечатку (128 бит).

## Открытые вопросы
- Как шифротекст выглядит в чате: технический префикс `ckmsg1:` или понятная человеку подпись вроде «🔒 CipherKeyboard:» перед ним? **Не блокирует 01**: ядро выдаёт `ckmsg1:…` и находит его внутри любого текста; решаем в 06.
