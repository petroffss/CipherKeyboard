# /review-loop — сборка с проверкой

Фича: $ARGUMENTS

Ты — **оркестратор**. Сам код не пишешь и evals не проверяешь: запускаешь агентов через Agent tool, ведёшь `specs/<фича>/state.md`, решаешь, что дальше. Каждый агент стартует в свежем контексте и не видит этот разговор и других агентов — поэтому они не соглашаются друг с другом по инерции. Передавай им в промпте всё нужное явно: пути к файлам, номер раунда, коммиты, список проблем. Файлы передавай путями, не пересказом.

**Лимиты**: не больше `max_rounds` раундов (по умолчанию 5). Проблема, которая пережила 2 раунда исправлений, — стоп. После 3 раундов ревьюер не ищет новое, а предлагает сменить подход.

## 0. Подготовка
1. `python3 .claude/scripts/pipeline.py show <фича>`:
   - `approved` → новый цикл;
   - `building` и есть state.md → продолжи с раунда из state.md (если `loop: needs-human` — сначала убедись, что пользователь ответил, и поставь `loop: running`);
   - `draft` / `in-review` → стоп: «Сначала /write-evals и /approve». Без одобренных evals не строим;
   - `verified` / `done` → спроси, что нужно сделать.
   Фичи из `depends_on` не в `done` — предупреди и спроси.
2. Git: `git status --porcelain` пуст (иначе спроси, что делать с изменениями). Ветка: `git switch -c feature/<фича>` от `main` (или `git switch feature/<фича>`, если есть). `base_commit` = `git rev-parse HEAD`.
3. Новый цикл: создай state.md по шаблону [templates/state.md](templates/state.md), `loop: running`, `round: 0`, `base_commit` и `last_reviewed_commit` = база.
4. `python3 .claude/scripts/pipeline.py set-status <фича> building`. С этого момента хук не даст закончить ход, пока evals не пройдены или цикл не остановлен по правилам ниже.

## Раунд N
В state.md: `round: N`.

### A. Builder — `Agent(subagent_type: "builder")`
Промпт:
- фича и пути: `specs/<фича>/requirements.md`, `evals.md` (контракт), `mockup.html`, `specs/_design/design.md` (если есть); номер раунда; `base_commit`;
- раунд 1: «Построй фичу целиком так, чтобы прошли все evals»;
- раунд ≥ 2: «Исправь только это» + открытые проблемы из state.md: провалы evals (ID, ожидание, что увидел verifier) и находки ревьюера «Важно» (класс, файл:строка, суть) + не больше 3 полезных «Мелочей». Для каждой находки с классом: «исправь этот класс во всём изменении, не только в указанном месте»;
- если ревьюер рекомендовал сменить подход — передай его рекомендацию дословно.
Builder возвращает: что сделал, вывод тестов/линтера/сборки, коммит `[ok]`/`[wip]`, вопросы.
Вопрос, меняющий продукт или evals → «Нужен человек».

### B. Verifier — `Agent(subagent_type: "verifier")`
Промпт: фича, путь к evals.md, раунд, «проверь **все** evals заново» (исправление могло сломать прошедшие).
Verifier ставит pass/fail с доказательством в evals.md и возвращает сводку. Проблема окружения (не стартует сервер, нет браузера) — реши сам, если можешь (команды в CLAUDE.md); иначе «Нужен человек».

### C. Reviewer — `Agent(subagent_type: "reviewer")`
Промпт: фича, риск, раунд, и режим:
- раунд 1 — **полный**: `git diff <base_commit>..HEAD`;
- раунд ≥ 2 — **только новое**: `git diff <last_reviewed_commit>..HEAD` + список уже сообщённых находок (ID, класс, место): «не повторяй, сообщай только то, что появилось или осталось в этих строках»;
- после 3 раундов, если проблемы остались, — **смена подхода**: «не составляй новый список; объясни, почему исправления не сходятся, и предложи другой подход».
После ответа: `last_reviewed_commit` = `git rev-parse HEAD`.

### D. Разбор (ты)
1. В state.md: строка в «Сводке», запись в «Журнале», новые находки с ID (`R1`, `R2`…) в «Открытые проблемы», исправленные — в «Закрытые», «Было до нас» — в свой раздел (не чиним в этом цикле).
2. **Повторы.** Тот же eval снова fail, или находка того же класса в том же месте → не заводи новую, увеличь «Подряд». Один класс в разных местах ≥ 2 раз → запиши в «Кандидаты в выученные правила».
3. Решение:
   - все evals `pass` и у ревьюера нет новых «Важно» → **Финал**;
   - у проблемы «Подряд» ≥ 3 (появилась и пережила 2 раунда исправлений) → **Нужен человек** (застряли);
   - N = `max_rounds` → **Лимит**;
   - нужен выбор, который меняет продукт, требования или evals → **Нужен человек**;
   - иначе → раунд N+1.

## Нужен человек / Лимит
1. В state.md: `loop: needs-human` (при лимите — `stopped`), заполни «Отчёт для человека»: что сделано, что не проходит и почему, что пробовали.
2. Покажи пользователю коротко: таблица evals (pass/fail), открытые проблемы, 2–3 варианта с рекомендацией (AskUserQuestion). Например: другой подход; упростить требование (evals меняются → `/write-evals`, `/approve` заново); принять с известным ограничением (только для low); отложить фичу.
3. После ответа: `loop: running` и раунд N+1. Продлить лимит можно только с явного согласия пользователя: `max_rounds` + 2.

Хук отпускает ход, только когда в state.md стоит `needs-human`, `stopped` или `done` — не ставь их, чтобы просто закончить работу.

## Финал
1. **Риск по факту**: скилл `classify-risk` с аргументом `diff`. Риск вырос (например, дифф затронул вход) → обнови `risk` в requirements.md и скажи пользователю.
2. **High**: запусти скилл `security-review` (встроенный `/security-review`). Его находки «Важно» → ещё один раунд builder → verifier (считается в лимит).
3. **Выученные правила**: из «Кандидатов» и проблем с «Подряд» ≥ 2 сформулируй по одной строке для REVIEW.md → «Выученные правила» (формат там). Если строке место в CLAUDE.md → «Соглашения» (чтобы builder не ошибался изначально) — предложи и туда. Спроси пользователя (AskUserQuestion, multiSelect), добавь только выбранные.
4. **Закрыть цикл**: state.md → `loop: done`; `python3 .claude/scripts/pipeline.py set-status <фича> verified`; коммит в ветку фичи: `[ok] <фича>: цикл завершён за N раундов`.
5. **Слияние**:
   - low → `git switch main && git merge --no-ff feature/<фича> -m "[ok] feature(<фича>): <название>"`, затем `set-status <фича> done` и коммит — low не требует приёмки человеком;
   - medium / high → ветку не вливай: принимает пользователь через `/approve <фича>` (для high — сначала `/first-time-user <фича>`).
6. **Итог пользователю** (как описание PR):
   - **Сделано**: 2–4 пункта.
   - **Проверка**: evals X/X pass, раундов N, что нашёл ревьюер и что исправлено.
   - **Риск**: уровень и почему.
   - **Как проверить руками**: 2–3 шага.
   - **Как откатить**: `git revert -m 1 <sha merge-коммита>` (или «ветка ещё не влита»).
   - Решения, принятые без пользователя, и правила, которые предложены.

## Экономия лимитов
- Агентам — пути к файлам, а не их содержимое.
- После раунда 1 ревьюер видит только новый дифф и не повторяет сообщённое.
- Мелочи не гоняют цикл: максимум 3 за раунд, и только вместе с «Важно» или провалами.
- `/first-time-user` в цикле не запускается — он отдельный шаг после.
