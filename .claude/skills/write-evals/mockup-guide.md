# Как делать mockup.html

Макет — эталон, с которым verifier сравнивает приложение, и дешёвый способ увидеть фичу до того, как на неё потрачены токены сборки. Это не прототип: без бэкенда, без логики.

## Требования

- **Один самодостаточный файл** `specs/<фича>/mockup.html`: CSS внутри `<style>`, без внешних скриптов и шрифтов (открывается офлайн, двойным кликом). JS — только чтобы переключать вкладки состояний, и то не обязательно.
- **Все состояния экрана** из раздела «Состояния экрана» в requirements.md: по умолчанию, пусто, загрузка, ошибка, успех, нет прав и т.д. Каждое — отдельная секция с заголовком и якорем `id="state-<имя>"`, чтобы eval мог сослаться на «состояние «Ошибка»».
- **Две рамки на каждое состояние**: десктоп (ширина 1280px, можно масштабировать через `transform: scale(.5)`) и мобильный (375 × 740px) — рядом, чтобы сразу видеть обе вёрстки.
- **Реальное содержимое**: правдоподобные имена, суммы, даты, длинные и короткие строки. Никакого lorem ipsum — на нём не видно, где текст ломает вёрстку.
- **Точные тексты**: заголовки, кнопки, подсказки и сообщения об ошибках — те же, что попадут в приложение и в evals.
- Шапка страницы: название фичи, список состояний со ссылками-якорями, дата.

## Единый дизайн

- Если есть `specs/_design/design.md` — следуй ему: палитра, шрифты, отступы, радиусы, компоненты.
- Если нет — первый макет его создаёт: вынеси токены в `:root { --color-… }` и опиши их в `specs/_design/design.md` (цвета, шрифтовая шкала, отступы, кнопка/поле/карточка/список). Следующие макеты и строитель используют те же токены.
- Тёмная тема — только если она есть в требованиях.

## Самопроверка перед показом

- Каждое состояние из requirements.md есть в макете, и наоборот.
- Мобильная рамка: нет горизонтальной прокрутки, кликабельные элементы не меньше 44px.
- Для каждого состояния есть eval с тегом [design], для мобильного вида — с [mobile].
