# /write-evals — контракт фичи

Аргументы: $ARGUMENTS — первое слово id фичи (`02-search` или просто `search`), остальное — описание новой фичи.

**Код приложения здесь не пишется.** Только файлы в `specs/<фича>/` (и `specs/_design/`).

## 1. Найти фичу
- `python3 .claude/scripts/pipeline.py show <фича>`.
- Не нашлась — создай `specs/NN-name/` (NN — следующий номер) и `requirements.md` по шаблону [templates/requirements.md](templates/requirements.md) из описания.
- Статус `approved` и дальше — evals уже одобрены. Предупреди, что изменение вернёт фичу на ревью, и спроси, продолжать ли.

## 2. Риск
`risk: unknown` → вызови скилл `classify-risk` для этой фичи и дождись результата. Риск задаёт строгость (шаг 4).

## 3. Требования
Доведи requirements.md до состояния, когда по нему можно строить без вопросов:
- истории и критерии приёмки — проверяемые (конкретные тексты, числа, переходы);
- все состояния экрана и граничные случаи; что не входит;
- неясности: реши сам разумно → «Решения, принятые без пользователя»; если решение меняет продукт → «Открытые вопросы» (спросишь в конце).

## 4. Evals
`specs/<фича>/evals.md` по шаблону [templates/evals.md](templates/evals.md). Каждый eval:
- один проверяемый факт: фиксированные шаги и точное ожидание (текст, URL, код ответа, количество);
- **Тип**: `ui` — сценарий в интерфейсе (браузер, симулятор или эмулятор — см. CLAUDE.md, «Платформа и интерфейс»); `test` — автотест, в том числе UI-тест (укажи файл и имя, строитель его напишет); `command` — команда и ожидаемый вывод; `design` — сравнение с макетом; `api` — запрос и ответ;
- **Почему провалит плохую работу** — какую типичную халтуру он поймает. Нет ответа — eval слабый, перепиши;
- **Статус**: `pending`.

Минимум по риску (его проверяет хук):

| риск | evals | [negative] | [security] | если ui: yes |
|---|---|---|---|---|
| low | 3 | — | — | [design]; для web ещё [mobile] |
| medium | 5 | ≥1 | — | [design]; для web ещё [mobile] |
| high | 8 | ≥2 | ≥1 | [design]; для web ещё [mobile] |

[negative] — неверный и пустой ввод, сбой сети или сервера, двойное нажатие, повтор запроса, прерывание посреди процесса.
[security] — без входа, чужой пользователь, подмена id в URL, запросе или deep link, инъекции, данные на устройстве, доступные другим приложениям.
Сценарии, которые проверяются только руками (например, системные настройки iOS), всё равно описывай как `ui` с точными шагами — verifier пройдёт их в симуляторе.

## 5. Макет (если ui: yes)
`specs/<фича>/mockup.html` по [mockup-guide.md](mockup-guide.md): один самодостаточный файл, все состояния экрана, каждое в рамках платформы (CLAUDE.md, «Рамки макетов»). Это эталон: verifier сравнивает с ним приложение.

## 6. Самопроверка (до 3 проходов)
1. `python3 .claude/scripts/pipeline.py check <фича>` — та же проверка, что в хуке. Исправь всё найденное.
2. Перечитай evals глазами халтурщика: «Как сделать фичу плохо и всё равно пройти все evals?» Нашёл способ — добавь или ужесточи eval.
3. Каждый критерий приёмки покрыт хотя бы одним eval; каждое состояние макета — eval [design].

## 7. На ревью
- `python3 .claude/scripts/pipeline.py set-status <фича> in-review`.
- Открой макет пользователю: `open specs/<фича>/mockup.html` (Linux — `xdg-open`). Дай ссылки на requirements.md и evals.md.
- Перечисли решения, принятые без пользователя, и открытые вопросы.
- Скажи, что дальше: посмотреть evals и макет (все рамки и состояния); правки — написать в чат; всё устраивает — `/approve <фича>`.

Одобряет только пользователь: статус `approved` ставит его команда `/approve`, хук не даст поставить его тебе.
Правки после ревью: внеси → шаг 6 → снова покажи. Статус остаётся `in-review`.
